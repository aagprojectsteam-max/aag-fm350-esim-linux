# 2026-09-24 FM350/T700 eSIM recovery and end-to-end validation

## Scope

This document records a real troubleshooting and recovery session on an HP EliteBook 840 G11 using the Fibocom FM350 / MediaTek T700 WWAN platform under Ubuntu Linux.

All subscriber-private identifiers are intentionally omitted. No activation code, EID, ICCID, IMSI, phone number, account credential, or private provisioning token is included.

Tested software/hardware details:

- Ubuntu 26.04 LTS
- ModemManager 1.25.95
- libmbim / mbimcli 1.32.0
- MediaTek/Fibocom PCI ID 14c3:4d75
- modem firmware 81600.0000.00.29.23.30_GC / F32
- hardware revision V1.0.6
- MBIM control device `/dev/wwan0mbim0`
- eUICC exposed on slot 2 on this machine

The incident contained multiple independent failures. Treating them as one problem led to misleading conclusions. The useful result of the investigation is the separation of those failures.

## Final result

End-to-end cellular data was restored.

The final validated state was:

- eSIM profile installed natively from Linux via SGP.22
- profile enabled
- SIM active
- modem enabled
- LTE registration state `home`
- packet service `attached`
- no network rejection
- NetworkManager WWAN profile connected
- IPv4 address assigned
- carrier DNS installed
- ICMP to 1.1.1.1 succeeded
- HTTPS request through the cellular source address returned HTTP 200
- WWAN disconnect/reconnect succeeded
- WWAN profile left with autoconnect enabled

## Failure 1: carrier/network registration rejection

### Symptom

The modem could be detected and the eSIM could be read, but network registration failed. Rejections observed during the investigation included:

```text
plmn-not-allowed (11)
apn-restriction-value-incompatible-with-active-pdp-context (112)
```

The 112 rejection was seen against multiple PLMNs during the failing subscription state.

### What was ruled out

The following were tested and did not remove the rejection:

- restoring the known working 3G/4G/5G mode set
- restoring Initial EPS settings
- restoring LTE attach configuration
- rebooting into a clean modem state
- keeping PCI runtime power management at `on` during isolation
- clearing a backed-up EF_FPLMN state once and verifying the readback
- testing a bounded PDP context and then removing it
- testing on both Linux and Windows with the vendor Windows driver

A historical PCIe/T700 recovery problem was also real, but a clean boot without a new AER failure still reproduced the network rejection. This separated the transport problem from the subscription rejection.

### Replacement subscription A/B result

An earlier replacement eSIM within the same problematic subscription did not resolve the registration rejection.

A newly created subscription with a newly issued eSIM was then installed. After carrier-side activation, the new subscriber identity registered successfully:

```text
registration-state: home
packet-service-state: attached
operator: 019 / 42501
network-rejection: none
```

This is strong evidence that the persistent Cause 112 state was subscription/provisioning-specific rather than a fundamental inability of the FM350/T700 or Linux stack to register.

The exact backend carrier database fault was not observable from the client side, so this document does not claim a more specific carrier root cause than the evidence supports.

## Failure 2: ModemManager enable loop caused by ATZ

### Symptom

ModemManager repeatedly entered:

```text
disabled -> enabling -> disabled
failed enabling modem: Unexpected data value
```

Debug logging isolated the exact command:

```text
ATZ
+CME ERROR: 59
```

At the same time, direct read-only modem checks showed:

```text
AT -> OK
AT+CFUN? -> 1
AT+CPIN? -> READY
FCC lock mode/state -> unlocked
```

Therefore the modem was responsive and radio/SIM state was usable; the generic V.250 `ATZ` initialization command was the operation failing.

### Tested downstream workaround

A downstream patch was built against the exact Ubuntu source package `modemmanager 1.25.95-1ubuntu1`.

The patch allows the first-enable initialization path to continue only when the initialization error is ModemManager's `MM_MOBILE_EQUIPMENT_ERROR_UNEXPECTED_DATA_VALUE`.

After installing the patched package, the same modem progressed:

```text
unknown -> disabled
disabled -> enabling
enabling -> enabled
```

Registration troubleshooting could then continue.

The exact tested patch is stored in:

```text
patches/modemmanager-1.25.95-fm350-atz-cme59.patch
```

### Important patch scope warning

The tested patch changes the generic `mm-broadband-modem.c` path. It is a downstream diagnostic/recovery patch, not an upstream-ready fix.

Before proposing upstream, the behavior should be scoped to the FM350/MTK/Fibocom modem class instead of affecting every modem that could return the same error class.

A rollback copy of the original installed ModemManager binary/package state was created before the live installation.

## Failure 3: eSIM enable returned APDU status 910B

During profile switching, the LPA helper returned an unexpected APDU status `910B` while enabling the profile.

The important observation was the post-operation readback: the profile was actually `enabled`.

Therefore a status error from the local helper must not be treated as proof that the profile state did not change. Always re-list/read back the profile state before retrying or deleting anything.

## Failure 4: stale NetworkManager SIM binding after eSIM replacement

After installing a different eSIM, an existing NetworkManager GSM profile still contained the previous `gsm.sim-id`.

The result was:

```text
No suitable device found for this connection
```

Fix:

1. read the current SIM/ICCID locally;
2. update the WWAN profile's `gsm.sim-id`, or create a fresh GSM profile;
3. never hard-code or publish the real SIM identifier.

A clean new NetworkManager profile was used during the final validation.

## Failure 5: MBIM bearer creation returned InvalidParameters

### Symptom

The new subscription registered successfully and packet service was attached, but NetworkManager could not establish the data bearer:

```text
registered -> connecting -> registered
MBIM status error: InvalidParameters
InvalidMandatoryInformation
```

Failed bearers showed combinations such as:

```text
apn: netazi
ip type: ipv4
allowed-auth: none, pap, chap, mschap, mschapv2, eap
```

Creating a second clean NetworkManager profile did not help while the authentication policy remained broad.

### Isolation tests

The following were used to prove the data path itself was viable:

- MBIM Device Caps query succeeded as root.
- MBIMEx version exchange succeeded with MBIM 1.00 / extended version 3.00.
- Direct ModemManager simple-connect with explicit `allowed-auth=none` succeeded.
- A direct MBIMEx v3 connection succeeded after a temporary AT-created data context was removed.
- The resulting bearer provided IPv4 address, gateway, DNS and MTU values.

The successful direct ModemManager test was:

```bash
mmcli -m <modem> --simple-connect="apn=<APN>,ip-type=ipv4,allowed-auth=none"
```

This proved that registration, MBIM and the carrier data path were working. The remaining failure was the NetworkManager bearer parameters.

### Working NetworkManager fix

On the tested NetworkManager 1.54.3 system, forcing no authentication and refusing all other authentication methods produced a working MBIM bearer:

```bash
nmcli connection modify "<WWAN profile>" \
  ppp.noauth yes \
  ppp.refuse-eap yes \
  ppp.refuse-pap yes \
  ppp.refuse-chap yes \
  ppp.refuse-mschap yes \
  ppp.refuse-mschapv2 yes
```

The tested WWAN profile also used:

```text
gsm.apn=<carrier APN>
gsm.home-only=yes
gsm.auto-config=no
ipv4.method=auto
ipv6.method=disabled
```

After disconnecting the manually created bearer and reconnecting via NetworkManager:

```text
wwan0mbim0  gsm  connected
modem state: connected
registration-state: home
packet-service-state: attached
network-rejection: none
```

A second disconnect/reconnect completed successfully, proving the result was not a one-shot session.

## Initial EPS settings used in the successful path

For the tested carrier configuration:

```bash
mmcli -m <modem> \
  --3gpp-set-initial-eps-bearer-settings="apn=<carrier APN>,ip-type=ipv4,allowed-auth=none"
```

After this operation the new subscription registered `home` and became `attached`.

Do not copy the APN blindly to another carrier.

## MBIM and AT observations

### MBIM health

Several early MBIM failures were misleading because of ownership/permission state. A meaningful health check must account for ModemManager/mbim-proxy ownership and permissions.

A successful root query was:

```bash
mbimcli -d /dev/wwan0mbim0 --device-open-proxy --query-device-caps
```

It returned the expected FM350/T700 device capabilities.

### MBIMEx v3

The modem successfully negotiated:

```text
MBIM version:          1.00
MBIM extended version: 3.00
```

The ModemManager 1.25.95 source also opens the MBIM port with Microsoft MBIMEx v3 support.

### Temporary AT PDP context experiment

A temporary PDP context was created during isolation testing. It proved that the modem/network could allocate a context and an address, but manual Linux routing over an ad-hoc WWAN link was not the final solution.

The temporary context was deactivated before the successful MBIM/NetworkManager path was validated.

Do not leave experimental `CGDCONT` / `CGACT` state active while testing MBIM bearer creation.

## PCIe / mtk_t7xx findings

A separate historical failure mode contained:

```text
PM configuration timed out
PCIe AER / Unsupported Request
device recovery failed
AT/MBIM write failures
```

During the 2026-09-24 investigation, PCI reset/reprobe work also demonstrated that ModemManager can rediscover WWAN ports in an incomplete state if restarted before the t7xx ports have fully settled.

Useful lessons:

- do not confuse PCIe transport failure with a carrier registration rejection;
- do not repeatedly reset/unbind the modem while debugging a network reject;
- after a hardware/PCI reset, wait for `t7xx_mode=ready`, WWAN ports, udev, and MBIM/AT nodes to settle before starting ModemManager;
- keep destructive recovery separate from registration/APN tests.

## FCC findings

FCC lock was explicitly checked and was not the blocker in this incident.

Observed read-only state:

```text
GTFCCLOCKMODE: 0
GTFCCLOCKSTATE: 0
GTFCCEFFSTATUS: 0,1
CFUN: 1
CPIN: READY
```

The ModemManager FCC-unlock support file for the FM350 PCI ID was also present.

## Clean troubleshooting order derived from this incident

When an FM350/T700 eSIM setup fails, use this order:

1. Confirm `t7xx_mode=ready` and AT/MBIM device nodes exist.
2. Confirm ModemManager discovers the modem.
3. Confirm the eSIM profile exists and read back its enabled/disabled state.
4. Confirm `CFUN=1`, SIM READY and FCC state.
5. If enable loops, capture ModemManager DEBUG and inspect the exact AT/MBIM command.
6. Separate modem enable state from registration state.
7. Record the exact network reject cause before changing APNs.
8. Disable NetworkManager autoconnect while running controlled registration tests.
9. Confirm `home/roaming` and `attached` before debugging the data bearer.
10. If NetworkManager returns `InvalidParameters`, compare the bearer properties with an explicit `mmcli --simple-connect` using only the intended authentication mode.
11. Reconnect once through NetworkManager after changing the minimal necessary profile settings.
12. Validate both IP reachability and HTTPS through the cellular source address.
